## 0. 项目一句话

**EchoTrace = 本机运行的「QQ 聊天记录导出 → 人物蒸馏 → 关系画像 → 对话求助」一体化工作台。**

全流程闭环（这是整个产品的骨架，任何功能都必须落在这条链上）：

    QQ 记录导出 → 导入清洗 → 一键蒸馏 → { 人格肖像 · 关系雷达 · 女娲 Skill · 重要话语 RAG }
                                            ↓
                                   与「他/她」对话 或 现实聊天求助
                                            ↓
                                     追加新记录 → 增量进化

## 1. 项目定位与边界

| 项 | 定义 |
|---|---|
| 名称 | EchoTrace（回声·痕迹） |
| 形态 | 本地单机 Web 应用（后端常驻进程 + 浏览器 UI），默认 `http://127.0.0.1:&lt;PORT&gt;` |
| 用户 | 单用户、本机、个人自用；不做账号体系、不做多租户 |
| 平台 | Windows 优先（开发目标机为 Windows），Linux / macOS 尽力兼容 |
| 数据 | 全部落在本机文件系统（SQLite + 向量索引 + 素材目录），**默认不上传任何数据** |
| 不做 | 不做 QQ 协议逆向、不自动发送消息、不做 SaaS、不做心理诊断 |

## 2. 目标用户与核心场景

**场景 A · 归档**
用户想把自己和一个重要的人的 QQ 聊天记录完整导出来存到本地，能看、能搜、能导出成别的格式，数据不能外泄。

**场景 B · 蒸馏**
用户希望把这个人「做成一个 skill」：让模型读完聊天记录，产出这个人的**人格肖像**、**关系指标（好感度、亲密度等，可视化雷达图）**、**女娲格式的人物 Skill**，以及**此人重要话语的 RAG 知识库**。

**场景 C · 求助**
之后用户跟这个（复刻的或真实的）人聊天，卡住不知道怎么回时，点「求助」：模型基于 **RAG 片段 + 最近 100 条对话 + 蒸馏出的该人人格 Skill**，给出 **Top 3 最优回复**，并说明每条的策略、依据与风险。

三场景对应三个必须打通的体验断点：
1. 导出 → 导入之间不能要求用户手工整理文件；
2. 蒸馏 → 复用的产物（人格、指标、Skill、RAG）必须自动落到该人物的档案里，下次开箱即用；
3. 求助必须**可解释、可溯源**，每条建议都能点回原始聊天记录。

## 3. 硬约束（不可协商）

| 编号 | 约束 | 验收方式 |
|---|---|---|
| **C1** | **数据不出本机**。除「用户显式触发的一次大模型 API 调用」外，任何聊天文本、图片、文件都禁止离开本机；禁止遥测、崩溃上报、云同步、第三方分析 SDK。 | 断网运行不崩溃；抓包只看到 LLM 域名 |
| **C2** | **零配置可启动**。一条命令拉起服务并打开浏览器；首次运行自动建库、建目录，不需要用户手动改配置文件。 | 干净机器上 `echotrace` 一条命令可用 |
| **C3** | **模型可插拔**。默认蒸馏/求助模型 = `deepseek-v4.1-flash`，默认思考深度 = `Max`；模型 ID、思考深度、温度、API Key、Base URL 全部在设置页可改，且有「连通性测试」按钮。 | 改配置后立即生效，无需重启 |
| **C4** | **一切结论必须可溯源**。人格结论、雷达分数、求助建议都必须携带 `evidence[]`，元素为 `message_id`，UI 上可点击跳转到原始消息。 | 任意结论都能一键跳回原文 |
| **C5** | **蒸馏产物 = 四件套**，固定落在 `data/people/{slug}/`：`persona.json`（人格肖像）、`radar.json`（关系指标）、`skill/`（女娲格式 Skill 目录）、`quotes.jsonl`（RAG 语料）。缺任何一件都算蒸馏失败。 | 蒸馏完成后目录结构可枚举校验 |
| **C6** | **只读，绝不代发**。系统禁止调用 QQ 的发送接口；「求助」只产出建议文本，由用户自己复制/粘贴。 | 代码中不存在发送类 API 调用 |
| **C7** | **许可证合规**。参考项目 [qq-chat-exporter](https://github.com/shuakami/qq-chat-exporter)（QCE）为 **GPL-3.0**：禁止复制/粘贴其源码进本仓库、禁止静态链接；只允许通过 **HTTP API 与导出文件格式**对接，并在 `NOTICE.md` 与关于页声明来源。EchoTrace 自身许可证由项目所有者决定。本机当前**未安装** QCE，应用只提供下载/安装引导，**禁止把 QCE 二进制打包进本仓库或安装包**。 | 代码中无 QCE 源码；NOTICE 存在；仓库内无 QCE 二进制 |
| **C8** | **诚实性约束**。模型产出的每一条判断都要区分「有原文支撑」与「模型推断」；推断项必须显式标注。禁止为了「画像好看」而编造聊天中没有的事实、口头禅、事件。 | persona.json 中推断项带 `inferred: true` |

## 4. 技术栈与工程结构

### 4.1 选型（推荐）

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Python 3.11+ / FastAPI / Uvicorn** | 仓库 `.gitignore` 已是 Python 风格；NLP、向量、数据处理生态最好 |
| 数据 | **SQLite（WAL 模式）** + `sqlite-vec`（向量）+ FTS5（全文） | 单文件、零运维、可备份、支持向量与关键词混合检索 |
| 模型层 | httpx 直连 OpenAI 兼容接口；**不引入重型 SDK** | 兼容任意 provider；deepseek / 本地模型可切换 |
| 前端 | **Vite + React + TypeScript**，UI 风格对齐 QCE（深色、左侧列表、右侧详情、卡片化） | 与参考项目观感一致 |
| 图表 | **ECharts**（雷达图 + 折线趋势） | 雷达图能力最完整 |
| 任务 | 自研轻量任务表 + asyncio 后台任务（状态机 `queued/running/paused/succeeded/failed/cancelled`） | 导出、蒸馏都是长任务，需要进度 / 取消 / 断点续跑 |
| 打包 | `pip install -e .` + 入口命令 `echotrace`；前端产物由后端静态托管 | 单机一条命令启动 |

**禁止**：把模型调用散落在业务代码里；所有 prompt 必须来自 `prompts/` 目录下的模板文件，代码只做变量注入。

## 5. 数据模型（核心表，字段即契约）

时间统一用 **Unix 秒（整数）**；所有 ID 用稳定哈希，保证重复导入幂等。

    -- 联系人（对方）
    contacts(id INTEGER PK, platform TEXT, uid TEXT, uin TEXT, display_name TEXT,
             alias TEXT, avatar_path TEXT, remark TEXT, created_at INTEGER,
             UNIQUE(platform, uid))

    -- 会话
    sessions(id INTEGER PK, contact_id INTEGER, chat_type INTEGER,   -- 1=私聊
             name TEXT, msg_count INTEGER, first_ts INTEGER, last_ts INTEGER,
             UNIQUE(contact_id, chat_type))

    -- 消息（核心表）
    messages(id INTEGER PK,
             session_id INTEGER,
             msg_id TEXT,                 -- 平台侧 ID（可能缺失）
             sender TEXT NOT NULL,        -- 'me' | 'them' | 'system'
             sender_raw TEXT,             -- 原始昵称，便于校验
             ts INTEGER NOT NULL,         -- Unix 秒
             kind TEXT NOT NULL,          -- text|image|emoji|voice|video|file|recall|system|json|reply
             text TEXT,                   -- 纯文本（表情转 [表情:名称]，图片转 [图片]，引用转 [引用:...]）
             reply_to TEXT,               -- 被引用消息的 msg_id
             raw JSON,                    -- 原始消息对象，永不丢字段
             hash TEXT NOT NULL,          -- sha1(session|sender|ts|kind|text)
             UNIQUE(hash))

    -- 重要话语 / RAG 语料单元
    quotes(id INTEGER PK, contact_id INTEGER, start_msg INTEGER, end_msg INTEGER,
           text TEXT, score REAL, dims JSON,     -- 可复用性/情感强度/关系意义/信息密度
           source TEXT,                          -- 'llm' | 'user_pick'
           embedding BLOB)

    -- 蒸馏产物索引（文件为真身，这里只做索引与版本）
    personas(id INTEGER PK, contact_id INTEGER, version INTEGER, created_at INTEGER,
             model TEXT, thinking TEXT, token_cost INTEGER, dir TEXT, summary TEXT)

    -- 关系指标时间序列（雷达图随时间演化的数据源）
    metrics(id INTEGER PK, contact_id INTEGER, period TEXT,   -- 'all' | '2026-01'
            key TEXT, value REAL, confidence REAL, anchor REAL, evidence JSON)

    -- 任务
    jobs(id TEXT PK, kind TEXT, status TEXT, progress REAL, stage TEXT,
         payload JSON, result JSON, error TEXT, created_at INTEGER, updated_at INTEGER)

    -- 设置（密钥单独存 data/.secrets.json，权限 600，不进 Git）
    settings(key TEXT PK, value JSON)

**清洗规则（必须实现且可配置）**：系统消息过滤、撤回消息标记、重复消息去重（`hash`）、连续刷屏合并、纯图片/纯表情消息保留但标记、长文本（>2000 字）截断并单独存档、发送人归一（昵称变化、群名片、`@` 前缀统一）。

**统计特征（`echotrace/stats/`，雷达的客观锚点，必须能离线算出）**：

| 特征 | 口径 |
|---|---|
| 消息条数比 | 对方条数 / 我条数 |
| 主动发起率 | 对方在「间隔 > 6 小时」后发出的第一条消息数 / 会话总数 |
| 回复时延中位数 | 对方对我方消息的首次回复间隔（分 P50 / P90） |
| 单条字数比 | 对方平均字数 / 我平均字数 |
| 深夜占比 | 23:00–03:00 消息占比 |
| 连续对话轮次 | 间隔 < 5 分钟的连续往返轮次分布 |
| 表情密度 | emoji / 颜文字 / 表情包 每百条 |
| 话题熵 | 关键词分布香农熵（话题广度） |
| 未来时态词频 | 「下次/以后/周末/回头/到时候」等每千条 |
| 情绪词分布 | 正向 / 负向 / 中性比例 + 方差 |
| 称呼变化 | 昵称、爱称、全名的出现时间线 |

## 6. 模块规格

> 每个模块都要给出：**入口 → 行为 → 产物 → 失败处理**。以下 M1–M8 是 M0 骨架之后的全部功能范围。

### M1 · QQ 聊天记录导出（参考 QCE 的 UI 与交互）

**目标**：让用户在本应用内完成「选联系人 → 选时间范围 → 导出 → 自动导入」，中间不需要手工拖文件。

**实现策略（三档，必须全部支持，按优先级降级）**

| 档 | 路径 | 说明 |
|---|---|---|
| **A（推荐 / MVP）** | **对接本机已部署的 QCE HTTP API** | QCE 在 `http://127.0.0.1:40653` 提供带 Token 的 REST API，直接触发导出任务并读取结果文件。EchoTrace 不复制其代码，仅走 HTTP + 文件（满足 C7）。 |
| **B** | **导入 QCE 已导出的文件** | 支持 `JSON / TXT / HTML / EXCEL / STREAMING_JSONL`。用户从 QCE 网页导出后，在 EchoTrace 里选文件导入（支持拖拽与批量）。 |
| **C** | **手动粘贴 / 自定义格式** | 兜底：`{时间} {发送人}: {内容}` 的纯文本，或用户自定义正则模板。 |

**QCE 对接细节（已核对官方文档，按此实现）**

- 基址：`http://127.0.0.1:40653`，网页控制台在 `/qce`；认证头 `Authorization: Bearer <QCE_TOKEN>`。
- QQ 号 → 会话 UID：`GET /api/users/lookup?uin={QQ号}`，成功返回 `{"success":true,"data":{"found":true,"uid":"u_xxx"}}`；`found:false` 时必须中止，**不要把纯数字 QQ 号当 peerUid 传**。
- 触发导出（推荐端点）：`POST /api/messages/roaming/export`，请求体：

      {
        "peer": {"chatType": 1, "peerUid": "u_xxx", "guildId": ""},
        "sessionName": "历史私聊",
        "format": "JSON",
        "filter": {"startTime": 1672574400, "endTime": 1704024000},
        "options": {"includeResourceLinks": true, "prettyFormat": true},
        "roaming": {"maxMessages": 50000, "maxSequenceQueries": 50000}
      }

  `filter.startTime / endTime` **必填、单位是 Unix 秒**（不是毫秒）；`format` 取值 `TXT|JSON|HTML|EXCEL|STREAMING_ZIP|STREAMING_JSONL`。
- 任务生命周期：`GET /api/tasks/:taskId`、`GET /api/tasks`（重连后恢复进度）、`POST /api/tasks/:taskId/cancel`、`DELETE /api/tasks/:taskId`（运行中删除返回 `409 TASK_STILL_RUNNING`，必须先取消）。
- 进度推送：WebSocket 事件 `export_progress` / `export_complete` / `export_error`；**必须同时实现轮询兜底**（WebSocket 断开不影响任务）。
- 文件读取：完成后用返回的 `filePath` / `downloadUrl` 取文件。
- 已知限制（UI 必须如实提示）：漫游导出**仅支持私聊（chatType=1）**，不支持群聊/频道；独立查看模式下返回 `503 STANDALONE_MODE`；任何响应都**不能证明腾讯服务端记录完整**（`serverCompletenessProven: false`），`partial: true` 时要在界面上标黄提示。

**UI（风格对齐 QCE）**
- 左侧：会话列表（头像、备注名、最后消息时间、条数），顶部搜索框支持 **QQ 号反查**。
- 右侧：会话详情 —— 时间范围选择（快捷：近 1 月 / 近 1 年 / 全部 / 自定义）、格式多选、资源下载开关、导出目录。
- 导出按钮的下拉菜单：**导出 / 漫游导出 / 定时备份**。
- 任务页：进度条、stage 文本、已扫描天数、`partial` 标记、取消按钮；完成后「下载 / 打开所在位置 / **一键导入 EchoTrace**」。
- 设置页：QCE 地址与 Token、连通性测试（显示版本、登录状态、STANDALONE 提示）。

**QCE 获取与安装引导（本机未安装，必做）**

用户答复：**本机目前没有 qq-chat-exporter**。因此导出中心首次进入先做检测（`GET /api/qce/detect` 探测 `http://127.0.0.1:40653`），未检测到时展示**引导页**，而不是空白页或报错弹窗：

1. **说明这是什么**：qq-chat-exporter（GPL-3.0，第三方开源）是一个本地运行的 QQ 导出工具；EchoTrace 只通过它的 HTTP API 读取导出结果，**不打包、不分发它的程序**。
2. **给出获取路径**：项目主页 `https://github.com/shuakami/qq-chat-exporter`；提供「打开 Releases 页面」按钮（调用系统默认浏览器打开链接，**不内置静默下载器**）与四步图文说明（下载 → 安装/解压 → 启动 → 在 QCE 网页控制台复制 Token）。
3. **回填与重检**：地址（默认 `http://127.0.0.1:40653`）与 Token 输入框 +「测试连接」按钮；成功后写入设置并自动回到会话列表。
4. **永远保留退路**：「我先用本地文件导入」按钮直达档 B —— **用户完全不装 QCE 也能用全部蒸馏 / 画像 / 雷达 / Skill / RAG / 求助功能**。
5. **禁止**：静默下载可执行文件、修改用户防火墙、要求管理员权限、自动启动第三方程序。

**失败处理**：QCE 未安装或未启动 → 走上面的引导页（不弹错误框）；401 → 提示 Token 失效并给出重新获取步骤；503 → 提示需完整登录环境；超时 → 保持任务可续跑。

### M2 · 导入与清洗

流程：**解析 → 归一 → 去重 → 过滤 → 入库 → 统计 → 分片**。

- 解析器要吃掉 QCE 的 JSON 结构（含 `elements` 数组：文本、图片、表情、语音、视频、文件、回复引用、系统提示），并保留 `raw` 字段兜底。
- 解析必须**流式**：`STREAMING_JSONL` 大文件不能整体读进内存（目标：100 万条消息可用，峰值内存 < 500MB）。
- 发言人归一：需给出「谁是我 / 谁是他」的确认界面，允许用户改判（导入后批量修正并重算统计）。
- 导入必须**幂等**：同一份文件导入两次，消息总数不变（靠 `hash` 唯一约束）。
- 导入完成后自动生成「数据体检报告」：条数、时间跨度、双方条数、媒体数量、疑似缺失月份、异常（空白消息、乱码）。**这份报告是用户决定「够不够蒸馏」的依据。**

### M3 · 一键蒸馏（核心功能）

**入口**：人物页右上角显眼的 **「开始蒸馏」** 按钮（这是产品的心脏，视觉权重最高）。点击后弹出配置确认框：

| 配置项 | 默认值 | 可改 |
|---|---|---|
| 模型 | `deepseek-v4.1-flash` | 是（下拉本机可用模型） |
| **思考深度** | **`Max`** | 是（低 / 中 / 高 / Max） |
| 时间范围 | 全部 | 是 |
| 蒸馏档位 | 标准 | 快速 / 标准 / 深度（对应采样量与阶段数） |
| 是否将聊天原文发送给模型 | 是（弹窗明示） | 是（可切「脱敏摘要模式」） |
| 成本上限 | 预估 × 1.5 | 是 |

**必须**在开跑前显示**预估耗时与预估 token 成本**，并明确告知：**本次蒸馏会把该人物的聊天内容发送给所选模型服务商**（这是 C1 的唯一例外，必须显式同意）。

**蒸馏管线（Map-Reduce，必须分阶段落盘、可断点续跑）**

1. **准备**：读统计特征 + 分层采样对话。采样规则（避免堆满上下文又丢关键信息）：
   - 全量保留：首月、最近 1 个月、关系转折点（间隔 > 30 天后的重启对话）；
   - 抽样保留：其余按「时间分层 + 长度加权」抽取约 20%；
   - 必抽命中：情绪词密集段、冲突段（负向词 + 短句 + 连续快速回复）、表白/承诺/告别类关键词段。
   - 分片大小 ≈ 8k~12k token，片间保留 300 token 重叠。
2. **Map｜分片证据抽取**（`prompts/distill_chunk.md`）：每片输出结构化事实 JSON（口头禅、表情习惯、情绪触发点、价值观线索、事件、称呼、关系信号），**每条附 `evidence: [message_id...]`**。逐片落盘到 `versions/v{n}/chunks/`。
3. **Reduce｜人格肖像终稿**（`prompts/distill_persona.md`）：合并全部证据 → `persona.json`。
4. **雷达评分**（`prompts/distill_radar.md`）：模型打分 + 统计锚点交叉验证 → `radar.json`。
5. **女娲 Skill 生成**（M5）。
6. **重要话语抽取**（M6）。
7. **收尾**：写 `metrics.json`、把版本快照归档、刷新人物页。

**并发与限流**：Map 阶段允许 2–4 路并发，必须带指数退避重试、超时、失败片单独重跑；任一阶段失败**不得丢弃已完成的分片**。

### M4 · 人格肖像 + 关系雷达

#### 4.1 人格肖像（`persona.json`，8 个板块，固定结构）

| 板块 | 内容要求 |
|---|---|
| `identity` | 称呼（含昵称/爱称时间线）、身份线索、关系定位、认识时长 |
| `language_dna` | 句长分布、标点习惯（连用问号/省略号/无标点）、高频词与专属用语、表情与表情包偏好、口头禅、说话节奏（先结论还是先铺垫）、复读/跟梗习惯 |
| `emotion` | 情绪表达方式（外放/内敛/阴阳）、触发点（什么话题会炸、什么话题会沉默）、安抚方式（怎么哄有效）、情绪周期 |
| `values` | 在意的东西（排序）、雷区、不能碰的话题、判断他人与事情的标准 |
| `interaction` | 沟通偏好（想被怎么回应）、讨厌的沟通方式、发起与收尾习惯、回复时延习惯 |
| `narrative` | 关系大事记（时间线，每条带 evidence）、关键转折、反复出现的共同话题 |
| `advice` | 「想让他/她开心可以怎么做」「想推进关系该聊什么」（附风险提示） |
| `unknowns` | 数据覆盖不到的空白、自相矛盾之处（**必须保留矛盾，不要和稀泥**） |

硬性要求：
- 每个结论字段形如 `{value, evidence: [msg_id...], inferred: bool, confidence: 0~1}`；
- `inferred: true` 的条目在 UI 上必须用不同颜色标记；
- 禁止出现聊天记录中不存在的具体事实（人名、地名、事件、口头禅）。

#### 4.2 关系雷达（8 维，0–100 分）

| 维度 | 含义 | 客观锚点（占 60% 权重） | 模型判断（占 40%） |
|---|---|---|---|
| **好感度** | 对你的正面情感倾向 | 正向情感词比例 − 负向比例；正向回应率（对你提议的接受比例）；表情密度 | 模型通读后的整体判断 |
| **亲密度** | 关系亲近与自我暴露深度 | 自我暴露类消息占比（家庭/私事/身体/工作烦恼）；日均消息量；深夜占比；爱称出现频次 | 同上 |
| **信任度** | 愿意托付与说真话的程度 | 求助类表达数；秘密/隐私分享数；负面情绪倾诉数 | 同上 |
| **依赖度** | 情感或事务上对你的依赖 | 「你觉得呢/怎么办/帮我」类句式频次；对你的作息跟随度；单方面发起的不对称度 | 同上 |
| **主动度** | 主动发起与主动关心的比例 | 主动发起率；主动开新话题占比；主动问候数 | 同上 |
| **情绪稳定度** | 情绪波动的幅度与恢复速度 | 情绪词方差；回复时延方差；单日情绪极性波动 | 同上 |
| **话题开放度** | 话题广度与敏感话题接受度 | 话题熵；敏感话题（前任/家庭/未来/金钱）回避率 | 同上 |
| **关系推进意愿（洽谈度）** | 愿意把关系往下一步推进的程度 | 未来时态词频（下次/以后/周末）；邀约接受率；计划类词汇 | 同上 |

**评分规则（必须实现，防止模型拍脑袋）**
1. 每个维度分别算：`anchor_score`（由统计特征映射到 0–100，映射表写在代码中且可调）、`model_score`（模型输出）。
2. 综合分 = `0.6 × anchor_score + 0.4 × model_score`。
3. **偏差告警**：`|model_score − anchor_score| > 20` 时，该维度在 UI 上标黄，并强制模型给出「为什么与统计特征不一致」的解释文本。
4. 每维必须输出：分数、置信度、趋势（近 30 天 vs 全期，↑/↓/→）、≥3 条证据。
5. 时间序列：按月计算同一套指标，供雷达图随时间滑动观看。

**UI**：雷达图（ECharts）居中；每根轴可点击展开右侧抽屉，显示评分依据、锚点明细、证据消息列表（可跳转）；顶部时间滑块（全部 / 近 1 年 / 近 90 天 / 近 30 天）；底部一行趋势折线（选定维度的月度变化）。

**必须附免责声明**：这些指标是对文本的统计与模型推断，**不是心理测评结论**，不构成对真实人物的准确描述。

### M6 · 重要话语 RAG

**语料抽取（`prompts/extract_quotes.md`）**
- 候选来源：对方发出的、非纯表情消息。
- 4 个维度打分（0–10）：**可复用性**（以后能否再提起）、**情感强度**、**关系意义**（承诺、表白、告别、和解）、**信息密度**（含可检索的事实）。
- 加权总分 → 取 Top N（默认 N = 会话条数的 3%，上限 2000 条）。
- **人工通道**：聊天记录浏览页支持右键「加入 RAG 语料库」，`source='user_pick'`，权重最高。

**切片策略（关键）**：不以单条消息为检索单元，而以 **3–7 条消息组成的对话窗口**为一个 chunk，保留 `start_msg / end_msg`，**确保召回时能还原上下文**。每条 chunk 记 `ts`、`speaker`、`topic`（模型打的短标签）。

**索引**：SQLite FTS5（中文需接 jieba 分词后写入分词列）+ `sqlite-vec` 向量索引；embedding 模型可配置（默认本地小模型，可选 API）。

**检索（混合）**：`BM25 召回 top 50` ∪ `向量召回 top 50` → RRF 融合 → 过滤（说话人 / 时间范围 / 会话）→ 可选重排 → 返回 top 8 并附原文与时间。

**UI**：人物页「语料库」Tab —— 列表 + 搜索 + 标签筛选 + 手动增删；每条显示原文、时间、得分与维度明细；支持导出为 `quotes.md / jsonl`。

### M7 · 对话与求助（Top 3 回复建议）

**两种模式，都要有：**

| 模式 | 说明 |
|---|---|
| **A · 与复刻人格对话** | 聊天窗里由「AI 版的他/她」按 persona + SKILL 扮演回复。用于练手、复盘、预演难聊的话题。界面上必须有明显的「这是 AI 模拟，不是真人」标识。 |
| **B · 现实对话求助** | 用户把真实对话（或手动粘贴的最近消息）放进来，卡壳时点「求助」，模型给出 Top 3 回复建议。 |

**求助入口**：聊天窗 `求助` 按钮（快捷键 `Ctrl+Enter`）；输入框连续 60 秒无输入且已有草稿时，浮出「要不要我帮你想一句？」的轻提示（可关闭，且必须可全局禁用）。

**输入装配（严格按 token 预算，超预算时按优先级裁剪）**

| 优先级 | 内容 | 预算 |
|---|---|---|
| 1 | 当前对话最近 **100 条**（可配置 20–200） | 保留最近 30 条原文，更早的压缩成滚动摘要 |
| 2 | 该人物 **SKILL.md 的浓缩版**（表达 DNA + 心智模型 + 反模式） | ≤ 3000 token |
| 3 | **RAG 召回 top 8**（含原文与时间） | ≤ 4000 token |
| 4 | **关系雷达摘要**（当前状态 + 近 30 天趋势） | ≤ 500 token |
| 5 | 用户草稿（若有） | 原样 |

**输出契约（必须是 3 条，策略必须分化）**

    {
      "options": [
        {
          "id": 1,
          "strategy": "稳妥型",
          "text": "……（可直接发送的回复原文，符合我平时的说话方式）",
          "why": "为什么这样说，结合 RAG 中的哪条记忆",
          "expected_reaction": "对方可能怎么回（预测 + 概率倾向）",
          "risk": "low",
          "evidence": [{"message_id": 12345, "quote": "……", "reason": "他曾说过……"}],
          "followup": "如果对方这样回，你可以接……"
        }
      ],
      "context_used": {"messages": 100, "quotes": 8, "skill": true, "radar": true},
      "token_cost": 12345
    }

三条的策略固定分化：**① 稳妥型**（低风险、维系关系）、**② 升温/推进型**（拉近关系、推进话题）、**③ 真实自我型**（不违心，表达真实想法，即使可能冷场）。

**回复风格必须模仿「我」的说话方式**（从我的历史消息中提取），而不是通用 AI 腔。因此蒸馏阶段必须额外产出一个 `self_style.json`（我自己的表达 DNA），供求助时注入。

**红线（必须硬编码拒绝）**：不生成 PUA、贬低、控制、欺骗、跟踪、情绪勒索类话术；不教用户伪造身份或编造事实；检测到用户表现出严重情绪危机时，给出关怀性提示并建议寻求专业帮助（不做诊断）。

**UI**：右滑抽屉展示 3 张卡片，并排可对比；每张支持「复制」「发送到输入框」「重新生成这一条」「收藏到话术库」；卡片内 `evidence` 可点击跳转到原消息。

## 9. 模型调用规范

1. **统一入口**：所有调用走 `echotrace/llm/client.py`，强制经过：模板渲染 → JSON Schema 校验 → 重试（3 次指数退避）→ 用量记账（写 `token_usage` 表）。
2. **默认参数（全部可在设置页覆盖，改后立即生效）**：API Key、Base URL、`model = deepseek-v4.1-flash`、**思考深度 = Max**；温度按任务给默认值（抽取/评分 0.2，画像终稿 0.7，求助建议 0.8）。**不得把模型 ID 硬编码在业务代码里**，只能作为默认值出现在配置模块中。
3. **思考深度是抽象层**：代码里只暴露 `thinking: 'low'|'medium'|'high'|'max'`，由 provider 适配器翻译成具体参数（不同提供商的字段名不同，例如 `reasoning_effort`、`thinking.budget_tokens` 等）。**在设置页可查看当前适配器实际发出的参数**，避免「以为开了 Max 其实没开」。
4. **结构化输出**：所有产物必须由 JSON Schema 约束并在服务端校验；校验失败 → 带着错误信息重试一次 → 仍失败则降级为「宽松解析 + 人工复核标记」，**不允许静默丢字段**。
5. **Prompt 文件化**：`prompts/*.md` 用 `{{变量}}` 占位；用户可在设置页查看与编辑（高级模式），修改后立即生效并记录版本。
6. **成本与超时**：单次任务有 token 上限与超时（默认 30 分钟）；超限前给出提示并支持「继续跑剩余部分」。
7. **降级档**：设置中的「脱敏摘要模式」= 不发送聊天原文，只发送本地预处理的统计特征 + 匿名化摘要（`A`/`B` 代称、去除手机号/地址/身份证/银行卡）。UI 必须说明：此模式下画像质量显著下降。
8. **多模态**：v1 不把图片/语音送入模型，只把「图片/表情/语音」作为消息类型与频率特征使用。图片内容理解列为 v2。

## 附录 B · 运行时提示词模板

这些模板落在项目 `prompts/` 目录下，用 `{{变量}}` 占位，由 `echotrace/llm/client.py` 渲染。**共性约定（每个模板都必须遵守）**：

1. 只输出 JSON，不要输出任何解释性文字、不要用 markdown 代码围栏包裹；
2. 不允许编造聊天记录里没有出现的事实；没有证据的判断必须标记 `inferred: true`；
3. 引用证据一律使用 `evidence_ids`，值为聊天记录里的 `message_id` 列表，**不得虚构 id**；
4. 证据不足时宁可少写、明确写「证据不足」，不要凑数；
5. 涉及情感与关系的判断，一律用「从文本中观察到的信号」表述，不做心理诊断。

### B1 · `prompts/distill_chunk.md` —— 分片证据抽取（Map 阶段）

```text
你是一个严谨的对话分析师。下面是一个人与「我」的 QQ 私聊记录片段（共 {{chunk_size}} 条，已按时间排序，格式为「序号 | message_id | 时间 | 说话人 | 内容」）。说话人 "{{target_name}}" 是本次分析对象，"我" 是记录的主人。

【任务】从这个片段里抽取关于 {{target_name}} 的**可复现证据**，不要下结论、不要写评价，只做「观察到什么」。按 6 个维度归类：

1. personality（性格倾向：外向/内向、直接/委婉、理性/感性等表现）
2. expression_dna（表达习惯：高频词、口头禅、句式长度、标点与语气词、表情包/emoji 使用、幽默方式、称呼方式）
3. emotion（情绪信号：开心、低落、烦躁、撒娇、回避、试探等，含触发情境）
4. interests（兴趣与关注点：话题、作品、游戏、人物、地点等）
5. relationship（关系信号：主动发起、回复速度倾向、是否愿意分享私事、邀约与拒绝方式、边界感）
6. events（事实性事件：约定、承诺、见面、变动、冲突、和解；带时间）

【输出格式】严格输出如下 JSON：

{
  "observations": [
    {
      "dimension": "personality | expression_dna | emotion | interests | relationship | events",
      "claim": "一句话描述你观察到的事实（不超过 40 字，只写现象）",
      "evidence_ids": ["message_id_1", "message_id_2"],
      "quote": "最能支撑该观察的原文片段（原样摘录，不超过 50 字）",
      "ts": "该证据发生的时间，格式 YYYY-MM-DD",
      "confidence": 0.0
    }
  ],
  "timeline_events": [{"date": "YYYY-MM-DD", "event": "事件描述", "evidence_ids": []}],
  "open_questions": ["这段记录里看不出来、但后续需要关注的问题"]
}

【规则】
- 同一个现象在多处出现，合并成一条 observation，evidence_ids 里列出最多 5 个代表性 id；
- confidence 取值 0.0~1.0：单条消息支撑给 0.3~0.5，同一模式在片段内重复出现 3 次以上给 0.6~0.8，有明确自我陈述（如「我就是这样的人」）给 0.8~0.9；
- 不要抽取「我」的性格，除非它反映了 {{target_name}} 的反应；
- 纯表情、纯图片、纯「嗯/哦/哈哈」这类无信息量的消息，只有在表达习惯维度才可引用；
- 片段内没有任何有效信息的维度，直接不要出现在输出里。
```

### B2 · `prompts/distill_persona.md` —— 人格肖像终稿（Reduce 阶段）

```text
你是人物画像撰写者。输入是同一段关系在多个时间片段的证据汇总（JSON 数组，每条含 dimension / claim / evidence_ids / quote / ts / confidence，已跨片段合并去重）。

统计事实（请作为写作底座，不要与它矛盾）：{{stats_json}}
（含：消息总数、双方条数、时间跨度、平均回复间隔、主动发起比例、消息类型分布、活跃时段、表情与语气词频次、话题分布）

【任务】输出这个人的**人格肖像**，8 个固定板块：

1. 身份与背景（能从聊天里推断出的：年龄段、职业/学业、城市、生活习惯、社交圈线索）
2. 性格底色（3~5 条，每条一句话 + 证据）
3. 表达风格（说话习惯、口头禅、称呼方式、标点与表情习惯，要给出真实例子）
4. 情绪模式（什么会让他高兴/低落/生气/回避，恢复方式）
5. 兴趣与生活（具体到名字：作品、游戏、食物、地点、人）
6. 关系互动方式（他如何对待「我」：主动程度、分享意愿、边界、冲突处理）
7. 价值观与在乎的事（他反复强调或明显在意的东西）
8. 与「我」的关系史要点（按时间排列的关键节点，带日期）

【输出格式】严格输出如下 JSON：

{
  "sections": [
    {
      "key": "identity | personality | expression | emotion | interests | relationship | values | history",
      "title": "板块中文标题",
      "summary": "该板块的总体描述，100~200 字",
      "items": [
        {
          "text": "具体表述（一句话，不超过 60 字）",
          "evidence_ids": ["message_id"],
          "inferred": false,
          "note": "当 inferred 为 true 时，说明推断依据；否则为空字符串"
        }
      ]
    }
  ],
  "portrait_markdown": "把上面 8 个板块整合成一篇 600~1000 字的人物肖像文章（第二人称「他/她」），可直接展示给用户",
  "tensions": ["这个人的内在矛盾或前后不一致之处，2~4 条，每条注明证据"],
  "unknowns": ["聊天记录不足以判断、但会影响理解的重要空白，2~4 条"]
}

【规则】
- 每条 item 必须至少有 1 个 evidence_ids；找不到证据的判断，inferred 置 true 并在 note 里写明推断链条；
- 证据冲突时不要掩盖：写成「早期……，后期……，可能发生了变化」，并在 tensions 里记一条；
- 禁止使用心理学诊断词汇（如「自恋型人格」「依恋障碍」），只描述可观察的行为模式；
- 不用「他可能是一个善良的人」这类无法证伪的空话；每句话都要能对应到记录中的具体表现；
- portrait_markdown 里保留 3~5 处关键原话引用，用「」标注，并保证引用与记录一字不差。
```

### B3 · prompts/distill_radar.md —— 8 维雷达评分

```text
你是关系状态评估者。输入：① 上一步产出的人格肖像 JSON；② 跨片段的证据汇总；③ 下列统计锚点（由本地脚本从聊天记录算出，是事实，不得被模型分数覆盖）：

{{radar_anchors_json}}

每维锚点的本地定义：
- affinity 好感度：正向表达占比、夸赞与关心类消息占比、负面表达占比的倒数；
- intimacy 亲密度：私密话题条数占比、深夜时段（23:00-03:00）消息占比、称呼亲密度（昵称/叠字/爱称有无）、自我暴露条数；
- trust 信任度：向对方求助/咨询/托付类消息占比、是否分享个人信息与烦恼、是否转述第三方隐私；
- dependence 依赖度：主动找对方解决事情的次数、对方未回复时的追问行为、情绪低谷期是否第一时间找对方；
- initiative 主动度：先发起会话的比例、单次连续发消息条数、主动约见/提话题次数、平均回复间隔与对方的差值；
- stability 情绪稳定度：情绪性消息占比、负向情绪持续时间、冲突后和解所需消息轮数；
- openness 话题开放度：话题类别数量、是否愿意聊新的陌生领域、回避话题的次数；
- progression 关系推进意愿：是否主动提及见面/未来计划/共同安排、对推进类提议的接受率。

【任务】为 8 个维度各给出：分数（0~100 整数）、置信度（0.0~1.0）、趋势（rising / flat / falling，基于前后半段对比）、至少 3 条证据、以及一句写给用户看的解读。

【计分纪律（关键）】
- 先根据统计锚点给出 anchor_score（0~100，映射规则见输入 JSON 里的 mapping_hint），再结合文本语义给出 model_score（0~100）；
- 最终分 score = round(0.6 * anchor_score + 0.4 * model_score)；
- 若 |anchor_score - model_score| > 20，必须在 conflict_note 里解释为什么文本印象与统计事实不一致（例如「统计上很主动，但主动都是为了办事而非闲聊」）；
- 数据量不足（如深夜消息只有 2 条）时，置信度必须低于 0.5，并在 note 里说明；
- 分数高不代表好、低不代表坏：如实给出，不要为了迎合用户而拉高。

【输出格式】严格输出如下 JSON：

{
  "dimensions": [
    {
      "key": "affinity | intimacy | trust | dependence | initiative | stability | openness | progression",
      "label": "中文名",
      "anchor_score": 0,
      "model_score": 0,
      "score": 0,
      "confidence": 0.0,
      "trend": "rising | flat | falling",
      "evidence_ids": ["message_id"],
      "interpretation": "一句话解读，不超过 50 字",
      "conflict_note": "仅当 |anchor_score - model_score| > 20 时填写，否则为空字符串"
    }
  ],
  "overall": {"score": 0, "stage": "关系阶段判断（熟悉期 / 升温期 / 稳定期 / 降温期）", "one_line": "一句话总结当前关系状态"},
  "highlights": ["最值得注意的 2~4 条发现，每条带 evidence_ids"],
  "warnings": ["需要用户留意的信号，如某维度持续下降"]
}

【语气约束】这是给普通用户看的结果：不要劝说、不要越界建议、不下「对方喜欢你 / 不喜欢你」的断言，只描述信号强弱，并说明样本局限（数据来自 {{record_span}}，共 {{msg_count}} 条）。
```

**渲染要求**：雷达图 8 个轴按上面 key 顺序固定；每个维度分数旁显示置信度小圆点；分数 < 40 的轴必须在解读里显式提示「样本不足或信号偏弱」。

### B4 · prompts/extract_quotes.md —— 重要话语抽取（RAG 语料）

```text
你是语料筛选员。下面是一段对话片段（{{chunk_size}} 条，「说话人 | 内容」格式）。你要挑出「这个人说过的、以后值得再被提起的话」。

【入选标准】满足任意一条即可入选：
1. 可复用性：以后能再提起（约定、计划、承诺、共同回忆、内部梗、绰号）；
2. 情感强度：明显的情感表达（表白、在乎、生气、道歉、安慰、告别）；
3. 关系意义：定义了关系的时刻（第一次约见、和解、边界声明、重要决定）；
4. 信息密度：包含可检索的事实（人名、地点、时间、偏好、禁忌、身体状况、工作学业信息）。

【排除标准】纯寒暄、纯表情、无内容的应答（嗯 / 哦 / 好的 / 哈哈）、广告、重复内容，以及不是 {{target_name}} 说的内容（除非这句话是对他的重要转述）。

【输出格式】严格输出如下 JSON：

{
  "quotes": [
    {
      "message_ids": ["message_id"],
      "text": "原话（一字不改，标点语气词都不改）",
      "ts": "YYYY-MM-DD",
      "topic": "主题短标签（2~6 字，如 约见面 / 工作吐槽 / 生日）",
      "reuse": 0,
      "emotion": 0,
      "relation": 0,
      "info": 0,
      "total": 0,
      "reason": "为什么值得记住，不超过 30 字",
      "sensitive": false
    }
  ],
  "context_notes": ["哪些信息必须连同上下文一起保存才不会被误解（反讽、玩笑、连续对话中的指代）"]
}

【规则】
- 四个维度各打 0~10 分；total = 0.35*reuse + 0.30*emotion + 0.20*relation + 0.15*info，保留一位小数；
- 一句话含多个要点时可拆成多条，但不要为了凑数重复；
- 反讽、玩笑、括号补白必须原样保留标点与语气词，否则语义会反转；
- 入选密度控制在每 100 条消息 3~8 条左右，不要整段照搬；
- 涉及第三方隐私的具体信息（住址、电话、身份证、银行卡）标记 sensitive: true，是否入库由本地脚本决定。
```

**入库要求**：抽取结果写入 quotes.jsonl 时，必须额外带上本地计算的 chunk 边界（start_msg / end_msg）与 people_id，确保检索命中后能跳转原文。

### B5 · prompts/advise_top3.md —— 大模型求助（Top 3 最优回答）

```text
你是「回复参谋」。用户正在和 {{target_name}} 聊天，不知道该怎么回，向你求助。

【你的输入】
1. 对方的人格档案（已从聊天记录蒸馏，可信度最高，请严格遵守他的说话方式与人际习惯）：
{{persona_json}}
2. 关系状态（雷达当前分数）：
{{radar_json}}
3. 用户自己的表达风格档案：
{{self_style_json}}
4. 检索到的相关历史片段（RAG，按相关度排序，含原文与时间）：
{{rag_snippets}}
5. 最近的对话（最新的在最后）：
{{recent_messages}}
6. 用户当前的困惑（可选）：
{{user_draft_or_question}}

【任务】给出恰好 3 条候选回复，且必须在三个方向上有明显分化：
- safe（稳妥型）：最不容易出错、不推进关系、给对方留空间；
- warm（升温推进型）：让对方感到被在意，可能小幅推进关系；
- honest（真实自我型）：最容易说出口、可能没那么体贴，但最像用户本人的风格。

每条都要说明：为什么这样说、依据是历史中的什么、对方大概率会怎么回、说错了有什么风险、如果对方那样回，下一步怎么接。

【输出格式】严格输出如下 JSON：

{
  "situation_read": "先用 2~3 句话读懂当前局面：对方现在的状态、这句话背后可能的意图、用户面临的选择是什么",
  "options": [
    {
      "strategy": "safe | warm | honest",
      "label": "策略中文名",
      "text": "可以直接复制发送的回复正文（必须模仿 {{user_name}} 的说话风格：句长、标点、表情习惯都要像他本人）",
      "why": "为什么这样回，60 字以内",
      "evidence_ids": ["支撑这条建议的历史 message_id"],
      "predicted_reaction": "对方可能的反应，以及这个反应意味着什么",
      "risk": {"level": "low | medium | high", "detail": "风险点"},
      "follow_up": "如果对方按预测回应了，用户的第二轮可以怎么说（一句话）"
    }
  ],
  "avoid": ["明确不建议说的 1~3 类话，并说明为什么（踩到他的雷区、与关系阶段不匹配等）"],
  "confidence_note": "这次建议的依据有多可靠：命中的历史片段数量、最近对话是否足够、有无明显未知因素"
}

【硬性规则】
- 三条回复的正文必须互不相似（不是同一句话的三种语气），也不能是模板式套话（「抱歉刚看到」「哈哈哈是吗」）；
- 必须模仿 {{user_name}} 本人的表达风格，而不是一个礼貌的 AI；不要书面语，不要堆砌客套词；
- 不要建议操纵、试探、冷处理、假意忽冷忽热等技巧；不要建议说谎或隐瞒；
- 不要断言对方的心思，用「可能」「从记录看他以前……」这种可证伪的表述；
- 证据不足（检索命中少于 2 条，或最近对话不足 5 条）时必须降低断言强度，在 confidence_note 里说明，并优先给 safe 策略；
- 回复长度贴合历史习惯：如果他平时一句话不超过 15 字，就不要给 60 字的长回复。
```

**UI 呈现要求**：三条建议并排成卡片，顶部先显示 situation_read；每张卡片显示策略标签、正文（可一键复制）、为什么、预期反应、风险徽章（绿/黄/红）；卡片底部可展开「依据的历史片段」（点击跳转原文）。用户点「采用了」后记入 local_actions 表，用于后续统计哪类策略更常被采纳。
